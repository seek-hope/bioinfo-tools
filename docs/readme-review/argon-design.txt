当前拟议实验已避开“毫秒级噪声”和“固定顺序”等旧陷阱，但在 i7-13700H 移动平台及无 root 约束下，仍存在几个足以推翻结论的审稿漏洞。以下为实验批评、最小矩阵、README 大纲及避坑建议。a) 最关键的实验漏洞及可执行修正混合架构与单核 CPU 预算失控： i7-13700H 包含 6P（12 逻辑核）+ 8E 核。仅声明“单核”不够，必须先解析 lscpu -e 确认拓扑，用 taskset -c <CPU_ID> 显式绑定到同一个物理 P 核的单一逻辑线程，且确保其 sibling 超线程无负载。更关键的是：不要相信命令行 -t 1 等于单核预算。Java (FastQC) 的 GC/JIT 线程、Python/C 库底层或外部 gzip 管道常在 -t 1 时派生后台线程；若不将整个进程树绑在单一逻辑 CPU 上，上游或 Rust 实现可能偷偷吃满多核，导致单核对比失效。多核测试同样需严格固定 P 核集合（如 taskset -c 0,2,4,6）。笔记本热节流与每次内联验证的发热干扰： 13700H 在不锁频时 Turbo Boost 衰减极快。若每次计时运行后立即执行解压、去 @PG 规范化、字节比对等重度 I/O 与 CPU 验证，验证阶段本身就会把 CPU 烤到降频，污染下一轮随机配对的计时。修正： 计时循环内只保留轻量级输出 hash/大小记录或将输出落盘（或 /dev/shm），等该组 5 次配对计时全部结束后，再集中跑正确性验证脚本；或在每对运行间加入基于 CPU 温度（如 sensors 降至阈值）或固定冷却间隔的停顿。Warm Cache 失效与 I/O 落盘噪音： 在 19GB 可用内存下，1000 万 reads 加上 BAM sort 临时文件或双端输出很容易冲刷页缓存，使“后跑者”退化为冷盘读取。此外，压缩级别一致不代表压缩库一致（系统 zlib vs zlib-ng vs bgzf），I/O 密集型子命令（如 fx、bam view）极易变成测压缩库而非核心算法。修正： 将单轮总工作集严格控制在可用内存的 50%（约 9GB）以内；主表优先测试“未压缩输入到未压缩输出（或 /dev/null）”以剥离 gzip 库差异，再单列一个端到端 .gz/.bam 案例反映真实流。UMI 合成数据的长尾与图拓扑缺失： 均匀随机生成的合成 UMI 和坐标无法触发 umitools dedup/group 的性能瓶颈。真实文库存在 PCR 扩增偏倚（Power-law 分布）及高频 UMI 团簇，1 步编辑距离构建的连通图（directional adjacency network）在稠密节点下耗时呈非线性暴增，且 BAM 是否预排序直接决定内存驻留窗口大小。修正： 合成 UMI 必须模拟非均匀簇大小（含高深度热点坐标和 1-2 bp 突变邻居），或者直接使用公开真实 scRNA/bulk UMI 小数据集切片；明确记录输入 BAM 的坐标排序状态。b) 最小且有说服力的测试矩阵（共 8 个核心 Case）避免 266 行全测，每个 CLI 选 1–2 个能代表计算/I/O
